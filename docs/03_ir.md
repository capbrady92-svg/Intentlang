# The IR — Intermediate Representation

The IR is the compiled, queryable graph that sits between your `.il` files and the generated code. Understanding it makes IntentLang dramatically more useful.

---

## What the IR Is

When you load `.il` files, the parser builds an **IR graph** — a flat, indexed, queryable representation of everything in your project:

- Every node from every file (models, features, routes, fields, rules, configs)
- Every edge (cross-file references, local relations)
- Global rules propagated from `core.il`
- Domain membership for every node
- Abstraction level for every node

The IR is what the transpiler actually operates on. It never reads `.il` source again after the IR is built.

---

## Node Anatomy

Every meaningful element in your `.il` files becomes a node in the IR.

```json
{
  "uid": "tasks:model:Task",
  "type": "model",
  "name": "Task",
  "filename": "tasks.il",
  "level": "high",
  "parent_uid": "tasks:domain:tasks",
  "children": [...],
  "block": true
}
```

UIDs follow the pattern: `{domain}:{type}:{name}`

Examples:
- `identity:model:User`
- `tasks:feature:Tasks`
- `billing:route:POST_/billing/checkout`
- `core:rule:anon_12`

---

## Edge Types

Edges connect nodes across files.

| Type | Meaning | Example |
|---|---|---|
| `xref` | Cross-domain reference | `Task.owner → @identity/User` |
| `relation` | Local model relation | `Task.project → Project` |

Every edge has:
- `from` — source node UID
- `to` — target node UID (or `unresolved:domain/Type` if not found)
- `resolved` — `true`, `false`, or not set for local relations
- `strictness` — `!`, `?`, or empty

## Querying the IR

Access the query engine with the `query` command:

```
il› query <your query>
```

### List nodes by type

```
il› query list models
[@high] model "User" (identity.il) uid:identity:model:User
[@high] model "Session" (identity.il) uid:identity:model:Session
[@high] model "Task" (tasks.il) uid:tasks:model:Task
[@high] model "Project" (tasks.il) uid:tasks:model:Project
```

```
il› query list features
il› query list routes
il› query list events
il› query list all         ← every node
```

### Show project info

```
il› query show stack
Stack: react + fastapi + postgres
Project: TaskFlow
Files: core.il, identity.il, tasks.il, platform.il

il› query show global rules
1. all endpoints require auth unless marked public
2. all models get id (uuid pk), created_at, updated_at
3. all errors return { code, message, trace_id }

il› query show domains
core: 8 nodes
identity: 31 nodes
tasks: 44 nodes
platform: 19 nodes
```

### Dependency queries

```
il› query deps of Task
tasks:model:Task →[relation]→ Project
tasks:model:Task →[xref]→ identity:model:User

il› query used by User
tasks:model:Task depends on identity:model:User via [xref]
tasks:model:Project depends on identity:model:User via [xref]
billing:model:Subscription depends on identity:model:User via [xref]
```

### Impact analysis

Run this **before changing anything**:

```
il› query impact of User
Direct dependents:
  tasks:model:Task [xref]
  tasks:model:Project [xref]
  billing:model:Subscription [xref]

Indirect (2nd-order):
  tasks:feature:Tasks
  tasks:route:GET_/projects/:id/tasks
  billing:feature:Checkout
```

This tells you exactly what needs to be regenerated if you change `User`. No surprises.

### Inspect a node

```
il› query inspect Task
{
  "uid": "tasks:model:Task",
  "type": "model",
  "name": "Task",
  "filename": "tasks.il",
  "level": "high",
  "children": [...],
  ...
}
```

Fuzzy matching — `inspect Auth` will find any node with "auth" in its name or UID.

### Show the dependency graph

```
il› query show graph
tasks:model:Task →[xref:owner]→ identity:model:User
tasks:model:Task →[relation]→ tasks:model:Project
tasks:model:Project →[xref:owner]→ identity:model:User
billing:model:Subscription →[xref:org]→ orgs:model:Org
```

## How the IR Helps the Transpiler

When you run `transpile tasks.il`, the transpiler doesn't just send the `.il` source to the LLM. It sends a carefully constructed context package built from the IR:

**1. IR Summary** — compact description of the whole project:
```
PROJECT: TaskFlow
STACK: react + fastapi + postgres
FILES: core.il, identity.il, tasks.il, platform.il
NODES: 112 total (4 models, 3 features, 8 routes)
EDGES: 7 (0 unresolved)
GLOBAL RULES:
  - all endpoints require auth unless marked public
  - all models get id (uuid pk), created_at, updated_at
  - all errors return { code, message, trace_id }
```

**2. Target file source** — the full `tasks.il` content

**3. Referenced domain files** — because `tasks.il` references `@identity/User`, the transpiler automatically includes `identity.il` as context

The LLM receives the IR summary first, giving it a complete system picture before it reads a single line of the target file. By the time it processes `tasks.il`, it already knows the stack, all global rules, and what the identity domain contains.

This is why the output is consistent. The LLM isn't guessing at conventions — they're in the IR summary it reads every time.

## Unresolved References

If a cross-domain reference can't be resolved, the IR flags it:

```
il› query show graph
tasks:model:Task →[xref:owner]→ unresolved:identity/User ⚠ UNRESOLVED
```

Causes:
- The referenced domain file isn't loaded
- The type name doesn't match exactly (case-sensitive)
- The domain name in the reference doesn't match the domain declaration

Fix: check `il› query show domains` to see what's loaded, verify the domain name matches.

Strict refs (`!`) block transpilation until resolved. Standard and optional refs (`?`) generate fallback code.

## IR in Practice

### Before making a change

```
il› query impact of User       # what will need regenerating?
```

### After adding a new domain file

```
il› query show graph           # confirm new cross-refs resolved
il› query list models          # confirm new models parsed
```

### Debugging a parse error

```
il› list                       # shows error count in status bar
il› query show graph           # check for unresolved refs
```

The IR rebuilds automatically every time you edit a file in the editor or run `load`. There's no manual rebuild step.

## IR Node Types Reference

| Type | Created by | Example |
|---|---|---|
| `project` | `project Name:` | `core:project:TaskFlow` |
| `domain` | `domain name:` | `identity:domain:identity` |
| `model` | `model Name:` | `tasks:model:Task` |
| `feature` | `feature Name:` | `tasks:feature:Tasks` |
| `route` | `route METHOD /path:` | `tasks:route:POST_/tasks` |
| `event` | `event name:` | `messaging:event:send_message` |
| `config` | `config Name:` | `platform:config:Database` |
| `field` | `name (type, mods)` | `identity:field:email` |
| `property` | `key: value` | (leaf, no uid) |
| `rule` | `- rule text` | (leaf, uid if inside rules block) |
| `xref_property` | `key: @domain/Type` | (becomes an edge, not a node) |
| `relation` | `name -> Target` | (becomes an edge) |
| `constraint` | `constraint: text` | (leaf) |
| `directive` | `@target: value` | (leaf) |
| `critical_path` | `critical_path name:` | `platform:critical_path:hot_loop` |
